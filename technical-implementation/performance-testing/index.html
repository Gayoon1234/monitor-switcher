Performance Testing

Hypothesis​

Scrolling lag may be caused by UI work increasing with the number of visible widgets. Activity pagination should keep rendered event cards bounded; device pages create one card per item. Separately, USB monitoring may delay the UI: the 500 ms poll calls synchronous Windows device enumeration.

Data/Results​

Measurements were collected on 22 and 24 November 2026 using synthetic UI data, configured activity history, and live Windows device/display discovery.

profile_activity.py copies the activity database to a temporary snapshot, times history loading/decoding, then measures repeated set_events() rendering. The source database is read-only. Activity displays 25 event cards per page.

measure_ui_responsiveness.py uses the production page widgets and automatically sends wheel events to scrollable areas. Synthetic data preparation and real data discovery are timed separately from widget construction. Real-data mode reads the configured activity period and a read-only database snapshot, USB devices through the Windows monitor, and displays through read-only discovery. Page actions and display selectors are disabled; the benchmark does not start the app's automation monitor or write to configuration, activity data, or display inputs. It records wheel-to-processed-widget-snapshot latency and lateness for a 16 ms Qt timer, including missed timer intervals. Snapshot latency includes event handling, event processing, and QWidget.grab(); it is not physical display frame presentation or a direct frame-rate measure.

Run from the repository root:

py perf\profile_activity.py --database activity.db --days 30 --repeat 5
py perf\benchmark_hardware.py --target usb --iterations 5 --warmups 1
py perf\benchmark_hardware.py --target displays --iterations 3 --warmups 1
py perf\measure_ui_responsiveness.py --page find-my-device --items 50 --scroll-events 200 --json
py perf\run_ui_benchmark_matrix.py --real-data --json

benchmark_hardware.py separately times live USB enumeration and display discovery. It queries monitor capabilities and current inputs but does not switch inputs or modify application data.

The My Devices run had no scrollable range with two saved cards, so it has no wheel or timer samples. Its approximately 3.96 s data-loading time includes live device/display discovery and is separate from the 34 ms widget construction time.

Synthetic comparisons at the same item counts were also run three times. At 306 Activity events, synthetic versus real widget construction was 30.76 ms versus 31.79 ms, with wheel p95 of 9.51 ms versus 8.79 ms. At 22 Find My Device cards, construction was 54.32 ms versus 72.19 ms, with wheel p95 of 9.83 ms versus 8.20 ms. My Devices at two saved cards had no scroll range in either case.

The totals and worst-case timings show occasional long UI-thread stalls as item counts rise, particularly at 5,000 items. The two-device Find My Device case has no scrollable range and is not included in this matrix.

Conclusion​

  • Overall, UI responsiveness looks good for the current real-world device counts; no immediate UI optimization is indicated. However, the device pages do not scale well to very large lists.
  • Activity stayed near 31 ms of widget construction from 50 to 5,000 synthetic events, consistent with rendering only its first 25 event cards.
  • Device-card construction and initial paint grew substantially at high synthetic counts. At 5,000 cards, worst timer lateness was 229 ms for My Devices and 436 ms for Find My Device.
  • With current real data (22 connected USB devices and 2 saved devices), the Find My Device page had a 6.37 ms median wheel response and one missed timer interval across three runs. My Devices had no overflow with two saved cards.
  • Data loading is a separate concern: My Devices real-data discovery took about 3.96 s, compared with about 34 ms for widget construction. Profile hardware discovery separately before attributing that delay to UI rendering.
  • Hardware profiling measured USB enumeration at a 395 ms median. The app polls every 500 ms on the Qt main thread, so each synchronous query occupies about 79% of that interval and is a strong candidate cause of recurring UI stalls. Display discovery took about 3.58 s for two displays, affecting startup/data loading rather than each USB polling cycle.
  • These are QWidget snapshot and event-loop measurements, not physical display frame times. They do not prove frame-rate or compositor behavior.
